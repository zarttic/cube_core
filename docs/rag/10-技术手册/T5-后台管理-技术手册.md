### 1.2 明确不负责什么

- 不做格网编码/剖分算法：T5 后端只消费 `ard_partition_batches` 等结果表，不实现格网逻辑。
- 不产生 ARD 剖分数据：ARd 数据载入与剖分在 T1/T2（同一后端进程内的 `routers/ard.py`、
  `services/order_watcher.py` 属于 T1 职责范围，本手册只描述与 T5 交界处）。
- 不做告警的对外通知（Alertmanager 未接线，见 9.4）。
- 不做 Prometheus/Grafana 自身的部署与规则维护：规则文件属于 `monitoring/`，代码只读其 API。

### 1.4 与其它 5 个子系统的边界

- **T1 ARD 数据载入**：T5 提供账号、权限、配额与审计；T1 在同一进程内产生订单/批次，T5 只读聚合展示。
- **T2 分析就绪数据剖分**：通过 `order_manage:*`、`data_import:*` 权限控制入口，不共享业务表。
- **T3 剖分数据服务 / T4 资源调度**：T5 只读其远端库的订单表（`order_mgmt.py:39`），写操作仅限订单状态回写。
- **T6 全球离散格网模型与编码**：T5 只统计其上报的瓦片调用量（`tile.type` 契约，见 `TILE_METRIC_REPORTING.md`）。

## 4. 对外接口契约

统一前缀来自 `main.py:390-398`：`/api`（认证、用户、监控、订单监控）、`/api/admin`（后台）、
`/api/order-mgmt`（订单管理）、`/api/storage`（`storage.py:15`）。
鉴权列中 **JWT** 表示 `Depends(get_current_user*)`（HTTPBearer，缺失时 FastAPI 默认返回
`401 {"detail":"Not authenticated"}`），**perm:X** 表示 `require_permission("X")`（不足时 403），
**super** 表示 `require_super_admin`（`admin.py:125`），**无** 表示代码中确实没有鉴权依赖。

## 8. 关键业务流程

### 8.1 本地账号密码登录（主流程）

1. 前端选择五种角色之一并提交账号口令（`Login.vue:268-274`、`Login.vue:490-502`）。
2. `login` 先 `init_default_admin` 兜底建号（`auth.py:697`）。
3. 按 `username` 查用户；若带 `noda_ticket` 则先从 Redis 取出并校验 `source=noda`（`auth.py:705-708`）。
4. 口令校验失败 → 写 `AUTH_LOGIN/failure` 审计并 401（`auth.py:711-720`）。
5. **角色一致性校验**：`user.role.value != credentials.role` → 401「角色不匹配」（`auth.py:726-735`）。
6. 状态非 ACTIVE → 403，并写审计（`auth.py:738-748`）。
7. 更新 `last_login/last_ip`，把该用户所有活跃会话置 `is_active=False`（单点在线）（`auth.py:751-763`）。
8. 新建 `UserSession`，写 `AUTH_LOGIN/success` 审计（`auth.py:765-781`）。
9. 签发 JWT（载荷含 `sub/role/user_id/is_super_admin/is_operator`，`security.py:39`），
   返回 `permissions` 与四类配额，并下发 HttpOnly Cookie `auth_session`（`auth.py:783-830`）。
10. 前端 `userStore.setUser` 落 localStorage（`store/user.js:27-34`），路由守卫按 `landingPath` 分流
    （`router/index.js:52-59`，守卫体 41-96）。

### 8.2 NODA 统一认证（两段式）

1. 用户点「NODA 统一认证登录」→ 浏览器跳 `/api/auth/noda/login`（`Login.vue:299`、`auth.py:416`）。
2. 后端 307 跳 `NODA_AUTHORIZE_URL`，参数 `client_id/response_type=code/scope/redirect_uri/state`
   （`auth.py:428-437`）。**实测（2026-09-12）**：`curl -s -o /dev/null -w '%{http_code}'`（GET）→ `307`；
   若用 `curl -sI`（HEAD）则为 `405`，响应头 `allow: GET`（见 10.表第 7 项）。
3. NODA 回调 `/api/auth/noda/callback`：code 换 token（Basic 认证头，`auth.py:530-560`）→
   `userinfo`（`auth.py:563-580`）→ `_find_or_create_noda_user` 建本地用户（默认「普通用户」+ 默认配额 + 拨备，
   `auth.py:335-398`）。
4. 落 `UserSession` + `AUTH_LOGIN/NODA统一认证登录` 审计，`create_access_token` 签 JWT 并
   `response.set_cookie("auth_session", ...)`，302 回前端 `?noda_login=1`（`auth.py:594-640`）。
5. 前端检测 `noda_login=1` 后调 `/api/auth/noda/session` 换回 Bearer 与档案（`Login.vue:395-406`、`auth.py:642`）。
6. **注意（已核实）**：真实回调路径**不要求二次本地口令**——步骤 3-5 之后直接建会话、签 JWT、下发
   HttpOnly Cookie 并跳转，前端用 `/api/auth/noda/session` 自动换登录态。手册初稿曾写“本地仍要求用户
   选择正确角色再提交一次本地账号口令”并引 `auth.py:468` 为证；该提示语位于**仅 `NODA_TEST_MODE=True`
   才可用的 mock 登录页**（`auth.py:439-468`），只描述 mock 分支：mock POST 走 `_issue_noda_ticket`
   （`auth.py:490-501`）→ 前端 `noda_verified=1&noda_ticket=...`（`Login.vue:390-393`）→ 仍需本地
   账号口令 + `noda_ticket` 调 `/api/login`（`Login.vue:490-502`）。快照内
   `NODA统一身份认证外部沟通需求说明.md`（2026-09-08）4.5 节的“回调未完成真正单点登录”结论已过时。
   回调失败一律 302 回登录页并带 `noda_error`（`auth.py:520-523`）。

### 8.3 TOTP 绑定与登录

1. 已登录用户 `GET /api/auth/totp/setup`：无 `totp_secret` 时生成 Base32 私钥入库，返回 `secret` 和
   `qr_code_url`（`auth.py:1071-1103`）。
2. `POST /api/auth/totp/confirm-bind`：`pyotp.TOTP(secret).verify(code)` 通过后置
   `is_totp_enabled=True`，写 `AUTH_MFA_BIND`（`auth.py:1111-1135`）。
3. 登录入口 `POST /api/login/totp`：未绑定 → 400；校验失败 → 写 `AUTH_TOTP_MFA/failure` 并 401；
   成功走与密码登录一致的会话/审计/发 token 逻辑（`auth.py:1137-1221`）。

### 8.4 生效权限解析（每个受保护请求都会执行）

1. `get_current_user` 解 JWT（`security.py:53`）；`get_current_user_obj` 回查用户并把最近活跃会话
   `last_active` 刷新（`security.py:64-83`）。
2. `require_permission(p)` → `has_effective_permission`（`security.py:85-95`、`permissions.py:114`）。
3. 判定顺序：超管直接放行 → 权限码不在目录内直接拒绝 → 个人补充权限命中 → 岗位模板命中（`permissions.py:114-126`）。
4. `require_operator` 走身份标记（`is_super_admin or is_operator`，`permissions.py:128`）。
5. 前端镜像同一套判定：`userStore.can(perm)`（`store/user.js:22-25`）与 `usePortalAccess.js:37-49`
   控制页面入口，`Admin.vue:3083` 控制模块页签。

### 8.5 用户创建 / 角色变更 → 资源拨备

1. `POST /api/admin/users` 校验用户名与邮箱唯一，按角色取 `USER_QUOTA_DEFAULTS` 写四类配额，
   `is_operator` 随角色置位（`admin.py:574-608`）。
2. 调 `resource_provisioner.provision_user_hardware`（`admin.py:607`）：
   - `minio_service.set_bucket_quota` 建桶并 `mc quota set ... --size <n>GB`（失败仅告警，`quota_checker.py:19-23`）；
   - Redis 写 `quota:user:<id>:api_limit`、`api_calls=0`、CPU 令牌列表、`storage_limit_gb`（`quota_checker.py:26-39`）。
3. 写 `USER_CREATE` 审计（`admin.py:616`）。
4. 角色变更时 `PUT /api/admin/users/{id}/role` 重算默认配额并再次拨备（`admin.py:339-360`）。

### 8.6 配额申请与审批

1. 用户 `POST /api/admin/quota-requests` 提交。配额类型枚举 `QuotaType` 共 **5** 个：`CPU核时`、`存储空间`、
   `API调用次数`、`GPU资源`、`网络带宽`（`schemas.py:292-297`）。但提交端点只映射 3 类
   （`quota_field_map` = `cpu_quota`/`storage_quota`/`api_quota`，`admin.py:748-752`）；不在这 3 类中的
   `GPU资源`/`网络带宽` 会直接 `400「无效的配额类型」`（`admin.py:753-755`），**不可申请**。
   写 `QUOTA_REQUEST` 审计（`admin.py:729-800`）。
2. 管理员 `GET /api/admin/quota-requests?status=`（需 `resource_schedule:view`）查看，
   `POST .../{id}/approve`（需 `resource_schedule:approve`）审批，可传 `final_value` 调整批准值；
   写 `QUOTA_APPROVAL` 审计（`admin.py:802-869`）。
3. 批准后**无条件**按 `quota_type` 写回 `users` 的 `cpu_quota`/`storage_quota`/`api_quota` 并同步 Redis
   （`admin.py:828-838`、`842-850`）；请求体 `QuotaRequestApproval` 只有 `approved`/`admin_comment`/`final_value`
   三个字段（`schemas.py:323-326`），**无 `quota_data`**，不存在“传不传 quota_data 决定是否覆盖”的分支。

### 9.2 API 限流中间件为死代码（关键发现）

`main.py:360`：

对 `/api/ard/*`：前两项为假、第三项 `path.startswith("/api")` 为真 → 提前返回；

### 大纲与代码的其他差异

1. 大纲表 59 假设“普通用户提交申请→管理员审批→配额值更新”。代码 `POST /admin/quota-requests/{id}/approve`
   在批准分支**无条件**把 `final_value or requested_value` 写回用户配额列并同步 Redis
   （`admin.py:828-838`、`842-850`）；请求体 `QuotaRequestApproval` 只有
   `approved`/`admin_comment`/`final_value` 三个字段（`schemas.py:323-326`），**不存在 `quota_data` 字段，
   也不存在“按是否传 quota_data 决定是否覆盖”的条件分支**（初稿此说法已核实为错）。
2. 大纲表 59 的“配额申请”覆盖 4 类资源，代码 `QuotaType` 实际有 5 个值
   （`CPU核时/存储空间/API调用次数/GPU资源/网络带宽`，`schemas.py:292-297`），但提交端点只接受前 3 类，
   `GPU资源`/`网络带宽` 一律 400（`admin.py:748-755`），而 `users` 表与配额展示页仍保留 `gpu_quota`。
3. 大纲称“后台管理系统”为独立系统；代码中它与管理后端是**同一 FastAPI 进程、同一数据模型**
   （`main.py:390-398`），前端是同仓库 Vue 工程的 `/admin` 路由。
4. 大纲表 60/61 面向“剖分数据服务”的操作；代码里瓦片统计入口对所有系统开放且**无鉴权**
   （`monitor.py:1099`），来源与使用者由 Span 属性自带（`user.name`、`tile.source`）。
5. 大纲表 59 将“存储权限”视为可配置项，但代码里 `storage:view`/`storage:operate` **无任何校验点**

   成员身份与 `user-<id>` 桶 owner 校验（9.8）。
6. 门户首页（表 64 相关）对**所有登录用户**开放，但首页轮询的 `/api/system/stats`、`/api/tile/*` 需要
   管理/导入类权限，普通用户会拿到 403 且页面静默降级为硬编码值（8.10）。
