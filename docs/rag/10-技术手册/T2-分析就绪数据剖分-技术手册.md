### 1.2 明确不负责什么

- **不实现格网算法**。定位、覆盖、拓扑、时空编码全部经 `grid_core.sdk.CubeEncoderSDK`
  调用 `cube_encoder`（`cube_web/cube_web/app.py:95` 构造 `sdk = CubeEncoderSDK()`）。
  本子系统不复制任何格网逻辑。
- **不做数据载入与元数据抽取**（属 T1 ARD 数据载入子系统）。剖分入参是载入系统交付的
  Dataset/Scene manifest。
- **不做地图服务发布**（发布动作写入 `partition_publications` 后交由 T3 剖分数据服务消费，
  见 `cube_web/cube_web/services/publication_service.py`）。
- **不做资源调度/配额治理**（属 T4）。本子系统只使用 Ray，不管配额与排队策略。
- **不做用户/权限主数据**（属 T5）。鉴权仅通过 Bearer Token 校验与角色归一化
  （`cube_web/cube_web/routes/auth.py:126` 的 `require_auth_for_api`，Bearer 校验在 `:136`–`:167`；
  角色归一化 `cube_web/cube_web/services/access_control.py:21` `normalize_role`、`:30` `is_admin_role`）。

### 1.4 与其它 5 个子系统的边界（一句话各自）

- **T1 ARD 数据载入**：负责把原始影像抽元数据、转 COG、写 `datasets/scenes/scene_bands`；T2 只消费。
- **T3 剖分数据服务**：负责对外地图/瓦片服务与检索；T2 只负责把瓦片置为 `published`。
- **T4 资源调度**：负责算力/存储配额与作业调度策略；T2 只按 Ray 连接串提交 Ray task。
- **T5 后台管理**：负责账号、角色、审计主数据；T2 只做 Bearer 校验和角色归一化。
- **T6 全球离散格网模型与编码**：提供 `CubeEncoderSDK`；T2 是其最大调用方。

## 4. 对外接口契约

### 4.0 鉴权与错误契约（所有 `/v1/*` 通用）

- 全局中间件 `require_auth_for_api`（`routes/auth.py:126`）只作用于 `/v1/` 前缀。
- **公开入口**：`POST /v1/partition/schemas/import`（`routes/auth.py:16` 的 `PUBLIC_V1_PATHS`），
  请求方 actor 固定为 `system:public-import`。
- **免登录但可选身份**：`POST /v1/client-errors`（`routes/auth.py:18` 的 `OPTIONAL_AUTH_V1_PATHS`）。
- 其余 `/v1/*` 需 `Authorization: Bearer <token>`；无凭证返回 401 `unauthorized`；
  需要管理员的方法返回 403（`require_admin`，`routes/auth.py:41`，基于
  `services/access_control.py:30` 的 `is_admin_role` 判定角色码 `ADMIN`）。
- 错误响应为 `{"error": {"code","message","request_id"}}`；仅当调用方显式传入 `detail`
  时响应体才额外带 `detail` 键（`services/api_errors.py:83`–`:85`），所以 401 会看到
  `"detail": "Missing Authorization header"`，而没有 detail 的错误不带该键。5xx 不回显内部细节
  （映射见 `app.py:212`–`:296`）。

### 5.2 关键关系

```text
load_batches ──< load_batch_scenes >── scenes ──< scene_assets ──< scene_bands(band_unit_id)
                                          │
partition_runs ──< partition_run_scenes ──┘
       │
       └── partition_data_unit_grid_status (band_unit_id, grid_type, grid_level)
                     │  partition_status / quality_status / ingest_status
                     │  output_version
                     ▼
        partition_output_versions ──< partition_output_chunks
              │                    ──< partition_logical_staging_rows
              ├──< partition_grid_cells
              ├──< partition_tiles ──< partition_indexes
              ├──< partition_quality_runs ──< partition_quality_results / partition_quality_errors
              └──< partition_publications ──< partition_publication_targets
```

- 一个 `load_batch_id` 可以对应多个 `partition_run_id`（一次运行可合并多个载入批次）。
- 剖分状态粒度是 `band_unit_id + grid_type + grid_level`，不是批次状态
  （`cube_web/docs/LOAD_BATCH_PARTITION_STATUS.md`）。
- `partition_data_unit_grid_status` 主键为 `(band_unit_id, grid_type, grid_level)`
  （`scene_domain_schema.py:230` 的 `ADD PRIMARY KEY`）。

### 8.2 逻辑剖分（`geohash` / `mgrs`）执行路径

1. 源对象按 URI 稳定哈希隔离下载到 `CUBE_SOURCE_CACHE_DIR`，双重校验远端 ETag 与本地 sha256；
   `_object_identity` 只接受 ETag，拿不到 ETag 时返回空串从而禁用缓存复用（不希望以 size 代替）
   （`cube_split/cube_split/jobs/ray_partition_core.py:104`、`_object_identity:187`）。
2. 逻辑剖分不切真实瓦片：写 `tile_kind='logical_reference'`（`partition_domain_schema.py:174`）
   与 `logical-chunks/*.jsonl.gz` staging 行（`partition_logical_staging_rows`），由 Ray worker 写 staging、
   再由 driver 侧 `promote_logical_staging` 集合式落库（见 8.1 步 10）。chunk 对象名与
   checksum 由 `jobs/logical_chunk_codec.py:29` 的 `logical_chunk_id` 和 gzip 结果 sha256 决定
   （`jobs/ray_logical_chunk_job.py:199`–`:202`，对象 key `…/logical-chunks/{chunk_id}.jsonl.gz`）。
3. 按 `CUBE_LOGICAL_SHARD_DEGREES` 分片、`CUBE_LOGICAL_SHARDS_PER_TASK` 打组、
   `CUBE_LOGICAL_MAX_IN_FLIGHT` 控并发（`jobs/ray_logical_chunk_job.py:102`–`:120`）。
4. 每个索引行的 `value_ref_uri` 形如 `s3://bucket/key#window=col_off,row_off,width,height`
   （`cube_split/cube_split/ingest/ray_ingest_job.py:285`–`:288`）。

### 8.3 ISEA4H 实体剖分执行路径

1. 作业入口强制 `grid_type=isea4h`，否则 `ValueError`（`jobs/entity_partition_job.py:73`）。
2. driver 不生成 `/tmp` COG：Ray 模式下由 worker 从 MinIO 取源并切瓦片（源已是 COG，**剖分链路不做
   COG 转换**，只经 `resolve_asset_source_path`/`cache_source_cog` 原样缓存），产物 `s3://` 实体瓦片同样由 worker 上传
   （`cube_web/docs/PARTITION_GRID_CONTRACT.md`；COG 转换属载入子系统职责）。
3. 生产实体剖分的空间分片数由并行度推导：`side = max(1, int(parallelism**0.5))`
   （`services/partition_dataset_runner.py:341`），分片数 `side²` 再截到 `parallelism`（`:355`）；
   `parallelism` 来自 `_entity_ray_parallelism()`（`:34`–`:41`，env `CUBE_ENTITY_RAY_PARALLELISM`，默认 16，
   即默认 4×4=16；若设为 8 则只有 2×2=4 个分片）。分片带固定 0.02° WGS84 重叠
   （`ENTITY_PLANNING_OVERLAP_DEGREES:46`，只有一个常量是固定的），driver 按 `output_id` 合并去重
   （`_group_entity_payloads:1319`、`group_merged` 累积于 `_run_entity_dataset_batch_on_ray:1390`）。
   `cube_web/docs/PARTITION_GRID_CONTRACT.md` 的“固定 4 x 4 共 16 个分片”只在默认并行度下成立；
   该文档已于 2026-09-18 补上“默认”与 `CUBE_ENTITY_RAY_PARALLELISM` 可覆盖的限定，与代码口径一致。
4. 上传与写库：`rs_entity_tile_asset`（`jobs/entity_partition_job.py:1056`）+
   `PartitionObjectStore.put_entity_tile`（`services/partition_object_store.py:27`：对象 key 带
   `version_prefix()` 的 `partition/{dataset_id}/versions/{output_version}/tiles/` 前缀，
   已存在同名对象时用大小+checksum 判等，不匹配抛不可变对象冲突）；
   MinIO 并发默认 16（`DEFAULT_ENTITY_MINIO_UPLOAD_WORKERS:58`）。
5. MinIO 凭据通过 `runtime_env.env_vars` 注入 worker，**不进 task 参数**
   （`jobs/entity_partition_job.py:982`）。
6. 实体瓦片读取自 2026-09-17（`56c4b13`）起是**分块流式**的：窗口像素超过
   `CUBE_ENTITY_READ_BLOCK_PIXELS`（默认 4,000,000 px）时不再一次性 `rasterio.mask.mask`，
   而是逐块读取+逐块掩膜写入 `CUBE_ENTITY_TILE_TMP_DIR` 临时 GeoTIFF，再流式 `fput_object`
   上传并删除临时文件（`services/partition_dataset_runner.py:1059`–`:1090`，实现 `_stream_entity_tile:114`）；
   小窗口仍走原快路径。峰值内存随块预算、不随格元大小增长（实测同格元 1.62 GB → 422 MB，
   31.6 s → 22.9 s，产物逐像素一致，见 `cube_web/docs/KUBERAY_OPERATIONS.md`）。

### 8.4 质检执行与导出的细节

1. 规则快照写入 `partition_quality_runs.rule_snapshot`（`quality_rules.py:172`），
   之后规则集变更不改写历史记录。
2. 执行时按快照校验 `implementation_version` 一致，否则运行失败
   （`quality_worker.py:275`–`:278`）。
3. 必选规则发现 → `fail` 并计入 `error_count`；可选规则发现 → `warn` 并计入 `warning_count`
   （`quality_worker.py:295`–`:297`）。
4. 单条规则异常：该规则结果写 `status='error'`、`execution_error` 脱敏，然后整轮终止为 `error`
   （`quality_worker.py:299`–`:315`、`_finalize_failed_quality_run:202`）。
5. 导出：`/results/export` 与 `/errors/export` 支持 `csv|json` 流式；
   `/export?format=xlsx` 生成成功/失败双 Sheet 工作簿（`quality_export.py:241`）。
6. 前端按钮：详情抽屉「重新提交失败数据剖分」（`PartitionQualityDrawer.vue:233`）与
   「导出质检结果」（`:241`，实际走 `?format=xlsx`，`stores/quality.js:323`）。

### A.2 文档与代码的“格网层级”口径不一致

`cube_web/docs/PARTITION_GRID_CONTRACT.md` 写 `mgrs` 层级为 `0..5`、`geohash` 为 `1..12`、
`isea4h` 为 `1..6`；而 `services/partition_defaults.py:7`–`:10` 的代码默认值是
geohash=4、mgrs=1、isea4h=6，`mgrs` 的分辨率启发式还会把 `resolution<10` 判为层级 1、
否则层级 0（`:84`–`:87`）。两者不冲突（范围 vs 默认值），但维护时需要同时看这两个文件。
10 s 性能基线（见文首）是调用方显式请求 `mgrs` L0 的结果，不经过该分辨率启发式。

### A.3 质检规则集版本已在主线收敛

工作区”两个口径；表 30/表 31 的清单可直接按 `dead6bf5` 核对。

### A.4 运行实例的 `CUBE_WEB_RAY_ADDRESS=auto` 已不再能连上 Ray

`GET /health?checks=config` 显示 `CUBE_WEB_RAY_ADDRESS` 来源为仓库根
`.cube_web.env`、值为 `auto`。该值只在“进程所在机器是 Ray 集群内节点”时成立。
2026-09-12 初版勘察时本机 `poufennode01`（`10.3.100.179`）确实跑着 raylet（连到已被弃用的
裸机 `10.3.100.182:6379`）；2026-09-17/18 复核时本机已无 raylet，`?checks=ray` 返回
`ConnectionError`。生产接入 KubeRay 后，该值只适用于在集群内跑的 Ray Job driver；
Web 服务自身提交作业应依赖 `CUBE_WEB_RAY_JOB_ADDRESS`（Jobs API），不要把
NodePort 写进 `CUBE_WEB_RAY_ADDRESS`（head 为 `--num-cpus=0`，外部 `ray.init` 在 0 worker 时必失败）。
