### 1.3 上游 / 下游

```
调用方(cube_split / cube_web / 外部服务)
   └─ grid_core.sdk.CubeEncoderSDK（进程内）  或  HTTP /v1/*（独立服务 50012）
        └─ GridService / TopologyService / CodeService
             └─ GridEngineRegistry（懒加载单例）
                  ├─ GeohashEngine（纯 Python）
                  ├─ MGRSEngine（mgrs 库 + pyproj + shapely）
                  └─ ISEA4HEngine（纯 Python 复刻 DGGRID v8.44 ISEA4H）
```

- 上游给它：经纬度点、GeoJSON 面、bbox、`GridAddress`、UTC 时间戳。它不接收栅格或文件。
- 下游拿它：`space_code[]`、`grid_level`、单元几何、ST code，用于索引入库、AOI 回读、检索与并行切分。

### 1.4 与其它 5 个子系统的边界

| 子系统 | 边界（一句话） |
| --- | --- |
| ①ARD数据载入 | 载入子系统只做登记与元数据标准化；格网绑定必须调 T6，不得自行实现编码 |
| ②分析就绪数据剖分 | 通过 `grid_core.sdk.CubeEncoderSDK` 取覆盖与编码（如 `cube_split/cube_split/read/aoi_reader.py:12,97`） |
| ③剖分数据服务 | 用 T6 编码做检索/下载寻址；编码生成不在服务侧实现 |
| ④资源调度 | 用 T6 的格网单元做任务切分粒度；调度本身不感知投影与拓扑 |
| ⑤后台管理 | 只展示配置与运行态；T6 的运行端点由环境变量/启动命令决定，不写入配置表 |
| Web 门户（②的前端入口） | `cube_web/cube_web/routes/sdk.py:51` 以进程内 SDK 复刻 `/v1` 契约，前端 `EncodingView.vue` 消费之 |

生产契约（`AGENTS.md` 与 `cube_encoder/CHANGELOG.md:22`）：`geohash`、`mgrs` 为逻辑剖分，
`isea4h` 为实体剖分；`s2`、`tile_matrix`、`plane_grid` 已从代码移除，作为历史格网不得再作为生产入口。
本包代码内检索 `s2|tile_matrix|plane_grid` 无任何命中（仅在测试文件名 `res2` 等子串出现）：

但工作区 `cube_encoder/grid_core/app/engines/__pycache__/` 下仍残留三个被移除引擎的历史字节码
（`s2_engine.cpython-311.pyc`、`plane_grid_engine.cpython-311.pyc`、`tile_matrix_engine.cpython-311.pyc`，
未跟踪且被 `.gitignore` 忽略）；校验“是否已移除”时必须加 `--include='*.py'`，否则会被这些 `.pyc` 误导。

### 4.2 各接口说明要点

- **`/v1/grid/cover` 的 compact 分支**：当 `boundary_type=bbox` 时走 `cover_geometry_compact`
  并把 `bbox` 反算成 `center`，返回的 `geometry` 恒为 `null`（`services/grid_service.py:82-101`）。
  当 `boundary_type=polygon` 时走 `cover_geometry`，返回带 `geometry` 的完整单元（`:103-104`）。
- **`/v1/topology/geometries` 的键**：`topology_code or "grid_type:grid_level:space_code"`，
  重复键只保留首个（`services/topology_service.py:28-31`）。
- **`/v1/topology/geometry` 的 bbox 模式**返回 `{"type":"BBox","bbox":[...]}`，不是 GeoJSON 标准类型（`topology_service.py:17-21`）。
- **`/v1/code/st` 的 `grid_level` 取自请求里的 `address.grid_level`**（`code_service.py:41`），
  不做与格网类型范围的二次校验。

## 5. 数据模型

### 5.1 本子系统不拥有任何数据表

`cube_encoder` 是纯库 + 无状态服务：无 `CREATE TABLE`、无 ORM、无 DSN（grep 实测无输出）。
因此第 5 节改为登记**契约数据模型**与**下游存储位置**。

| 模型 | 字段 | 代码位置 |
| --- | --- | --- |
| `GridAddress` | `grid_type:str`、`grid_level:int`（单元自身层级）、`space_code:str`、`topology_code:str\|None` | `models/grid_address.py:6-18` |
| `GridCell` | 继承 `GridAddress` + `center[2]`、`bbox[4]`、`geometry?`、`metadata{}` | `models/grid_cell.py:10-20` |
| `CompactGridCell` | 继承 `GridAddress` + `bbox[4]` | `models/compact_grid_cell.py:8-15` |
| `STCode` | `grid_type`、`grid_level`、`space_code`、`time_code`、`st_code` | `models/st_code.py:4-14` |
| `BaseResponse` | `warnings[]`、`statistics{}`（所有响应共用） | `models/response.py:16-18` |

`topology_code` 语义（重要）：三类标准引擎**一律返回 `None`**（实测 geohash/mgrs/isea4h 的
locate、cover、cover_compact、neighbors 结果全部为 `None`）；
字段仅为读取历史记录保留（`models/grid_address.py:12`、`CHANGELOG.md:18`、`docs/ARCHITECTURE.md:27`；
`docs/README.md` 全文未提及该字段）。
MGRS 历史扩展码格式仍可解析：`^mgrs-topo-v1:(utm-<1..60><n|s>|ups-[ns]):([0-5]):([0-9A-Z]{3,15})$`
（`engines/mgrs/address.py:1,12-14`；解析入口 `parse_topology_code`（`:89`））。
构造侧 `build_topology_code`（`engines/mgrs/address.py:101`，校验 96 ASCII 字节上限）在生产代码中
**无任何调用点**（`grep -rn build_topology_code cube_encoder --include=*.py` 仅命中定义本身、
`build/lib` 的历史副本与 `tests/test_mgrs_address.py:99` 的往返测试），属与 9.9/9.11 同类的不可达代码：
当前实现只能解析历史码，不能生成新码。

### 5.3 ISEA4H 编码模型（`space_code` 语义）

| 项 | 值 | 代码位置 |
| --- | --- | --- |
| 编码 | 未补零的十进制 DGGRID `SEQNUM`，1 基 | `docs/README.md:38`、`isea4h_engine.py:81-88` |

## 8. 关键业务流程（逐步，带代码位置）

### 8.1 点定位（locate）主流程

1. `POST /v1/grid/locate` 进入 `grid_core/app/api/grid.py:12`。
2. Pydantic 校验 `extra="forbid"`、层级范围、经纬度范围：`models/request.py:42-59` → `:23-31`。
3. `GridService.locate` 再做一次层级校验并取引擎：`services/grid_service.py:17-22`。
4. `GridEngineRegistry.get_engine` 懒加载单例：`engines/registry.py:34-41`。
5. 引擎分支：
   - geohash：`_encode(lon,lat,precision)`（`geohash_engine.py:86-123`），`grid_level = len(code)`（`:185-187`）；
     经度 180° 归一为 −180°，纬度 90° 用 `math.nextafter` 下压（`:74-84`）。
   - mgrs：`mgrs.MGRS().toMGRS(lat, lon, MGRSPrecision=level)` 后规范化（`mgrs_engine.py:55-70`）；
     `grid_level = 精度`（0=100 km … 5=1 m，类文档串 `:33-42`，精度对照表在 `:36-41`）。
   - isea4h：`locate_cell → q2di_to_seqnum`（`isea4h_engine.py:166-170`、`isea4h/addressing.py:485-491,139-147`）。
6. 返回 `GridCell`（geohash 无 geometry、mgrs/isea4h 带 `geometry`）：
   `geohash_engine.py:189-201`、`mgrs_engine.py:144-160`、`isea4h_engine.py:143-153`。

### 8.2 区域覆盖（cover）主流程

1. `POST /v1/grid/cover`（`app/api/grid.py:18`）→ 校验层级（`request.py:71-76`）。
2. `GridService.cover`：CRS 必须 `EPSG:4326`（`grid_service.py:74-75`）；
   `geometry` 为空时用 `bbox_to_polygon` 转换，日期变更线跨越返回 `MultiPolygon`（`:76-78`、`utils/geometry.py:32-51`）。
3. 路径选择：`boundary_type=bbox` → `cover_geometry_compact`（`:82-101`）；否则 `cover_geometry`（`:103-104`）。
4. 引擎差异：
   - geohash：先用 AOI 外接框枚举同层候选，再按面积相交/包含筛选（`geohash_engine.py:483-528`）；
     `minimal` 仅在 `compact=True` 时把 32 个同父兄弟合并为父单元（`:530-552`）。
   - mgrs：代表性点做种子 → 沿 UTM/UPS 邻域 BFS 扩散 → 按正面积相交/完全覆盖筛选（`mgrs/cover.py:30-99`）；
     `minimal` 走 `_coarsen_minimal`（`:96-97,268`）。
   - isea4h：局部 AOI 用连通分量种子 + 六边邻域遍历；跨日期变更线/极区/大范围 AOI 改用
     STRtree 全球索引，`cell_count(level) > 200000` 时不建索引（`isea4h_engine.py:209-264`）；
     `minimal` 先按低分辨率贪婪取整单元，再对残余区域细化（`:340-359`）。
     **索引缓存是进程级且永不失效**：`_COVER_INDEX_CACHE: dict[int, tuple[object, list[object]]] = {}`
     （`isea4h_engine.py:38`）按 `level` 缓存该层全部单元的外接框，命中后一直驻留内存（`:269-276`），
     既无容量上限也无清理/失效入口（全仓 `grep _COVER_INDEX_CACHE` 仅命中 `:38,269,276`）。
     长驻服务（见第 2 节）处理过大范围 AOI 后这部分内存不会归还，要释放只能重启进程；
     而同一缓存又是有意为之的性能手段（避免重复枚举 20 万量级单元），选型时需一并考虑。
5. 响应 `statistics.cell_count = len(cells)`（`app/api/grid.py:33`）。

### 8.3 拓扑主流程

1. `POST /v1/topology/{neighbors,parent,children}` → `TopologyService`（`topology_service.py:12,34,38`）。
2. geohash 邻接用“解码中心 + 步长 → 重编码”求 8 邻域（`geohash_engine.py:219-285`）；
   父级去掉最后一位（`:433-438`）；子级逐层追加 base32 字符（`:440-457`）。
3. mgrs 邻接按投影偏移生成候选并逐一带域校验（`mgrs/topology.py:38-91`）；
   父级与子级按标准 MGRS 补零规则（`:226,239`）。
4. isea4h 邻接/父子走 Q2DI 邻域表（`isea4h/topology.py:49,69,116`）；
   五边形邻居 5 个、子单元 6 个；**子级仅支持 `res+1`**（`:77-78`）。

### 8.4 时空编码生成与解析

1. 生成：`/v1/code/st` → `CodeService.generate_st_code`（`code_service.py:29-44`）→ `to_time_code`
   做 UTC 归一化与格式化（`utils/timecode.py:15-25`）→ `build_st_code` 拼装（`code_service.py:46-63`）。
2. 批量：`/v1/code/st/batch` → `build_st_code_strings`，要求两个列表等长（`code_service.py:95-112`）。
3. 解析：正则拆 4 段（`utils/validator.py:8-17`）→ 前缀反查格网类型（`code_service.py:65-70`）→
   时间码按长度匹配格式并 `strptime` 校验（`:114-122`）；非法长度/取值抛 `VALIDATION_ERROR`（观测为 422）。

### 8.5 MGRS 单元几何生成（裁剪链路）

1. `_clipped_geom` 先由 `space_code` 推断 UTM/UPS 域（`mgrs_engine.py:138-142`、`mgrs/topology.py:269`）。
2. 投影方格按边长密化（8 段/边，`mgrs/geometry.py:21,51`）→ 逐点反投到 WGS84（`:62-73`）。
3. 与有效域多边形求交（`domain_polygon`，`mgrs/domain.py:91-133`），空几何抛错（`mgrs/geometry.py:153-191`）；
   `metadata` 返回 `{"precision": level, "domain": domain.token}`（`mgrs_engine.py:154-157`，两个键在 `:155-156`）。

### 8.6 失败/重试路径

| 场景 | 系统行为 | 代码位置 |
| --- | --- | --- |
| 层级越界 | Pydantic 422（`detail` 结构）或业务 422（`error` 结构） | `request.py:23-31`、实测 10.3 |
| 非法 `space_code`（geohash 大写/非 base32） | `VALIDATION_ERROR` | `geohash_engine.py:164-176` |
| 非法 isea4h seqnum | `VALIDATION_ERROR`，"out of range at resolution" | `isea4h_engine.py:404-414` |
| CRS 非 4326 | `VALIDATION_ERROR` | `grid_service.py:74-75` |
| 空几何 | 返回 200 + 空 `cells`（非错误） | `geohash_engine.py:500-501` |
| 性能烟测超阈值 | `run_perf_smoke(enforce=True)` 抛 `RuntimeError` | `perf_smoke.py:196` |
| 引擎裸 `ValueError`（如 isea4h 跨级 children / res0 parent） | **500**，无重试、无降级 | 见 9.1、9.2 |

本子系统**没有任何重试/退避/熔断代码**（grep 无 `retry`、`backoff`），失败即向调用方暴露错误；
重试由 ④资源调度或调用方作业层负责。

### 8.7 离线权威向量生成流程（仅维护期使用）

1. 需要 DGGRID v8.44 可执行文件（`DGGRID_BIN` 或 `.dggrid_src/build/.../dggrid`）：`tools/generate_isea4h_vectors.py:51-61`。
2. 写入元数据文件：`ISEA4H + ISEA + HEXAGON + PURE aperture 4 + WGS84_AUTHALIC_SPHERE + 朝向(11.25,58.28252559,0) + SEQNUM`：`:32-47`。
3. 以 `GENERATE_GRID` 出全球网格，逐分辨率产出中心点、邻居（res0-4）、子单元（res0-3）：`:85,104,122`。
4. 结果落 `tests/fixtures/isea4h/*.jsonl`，sha256 冻结在 `tests/test_isea4h_fixture_manifest.py:12-29`（16 个条目），
   向量计数断言在 `:51`。
5. 运行时只读 JSONL，不调用 DGGRID。

| 大纲表号 | 大纲功能名 | 状态 | 代码证据 | 说明 |

1. **大纲的“层级”概念**在实现中拆成两个字段：请求侧 `requested_grid_level` 与返回侧 `grid_level`；

## 附录：勘察中的重大发现

1. **ISEA4H 拓扑存在两处未处理的裸 `ValueError` → HTTP 500**（9.1、9.2）。这是本子系统当前唯一会
   产生 5xx 的路径，且都能被远端请求直接触发（`address.grid_level` 不在请求模型校验范围内）。
   建议在 `isea4h_engine.py:387-396` 或 `topology_service.py:34-40` 把 `ValueError` 转成 `ValidationError`。
2. **`cube_encoder` 并不是“页面级”交付物**。表66~70 面向 Web 页面，页面实现在 `cube_web` 前端；
   若验收按大纲逐条点验，必须在 `cube_web`（50039 + 50040）运行状态下进行，而不是在 50012 上。
   本手册第 11 节已逐表标注实际证据位置。
3. **`DGGSCode.zip` 与真实基线脱节**（9.7）：压缩包是 AIRCAS 的 Java 参考实现，被 `.gitignore`
   排除、无任何代码引用；实际 isea4h 权威基线是 `.dggrid_src`（DGGRID v8.44 源码与本地构建二进制）
   生成的 16 个 JSONL。交接时若只复制仓库，将同时缺失两者（`.dggrid_src` 也被忽略）。
4. **`geohash_engine.py:36-65` 的坏死代码与占位串**（9.9）：常量表 `_NEIGHBOR_MAP` 的 8 行里共 18 处
   `telegram` 字面量（全文件 19 处，另 1 处在 `:62` 注释），`_BORDER_MAP` 则不含占位串，
   一段“待补全”的开发注释留在生产文件中。功能不受影响，但会严重误导后续维护者。
5. **CI 性能门禁名不副实**（9.8）：阈值文件仍是 S2/H3 时代的变量名，`_env_float` 静默回落默认值，
   使 CI 实际门槛与文件内容不一致；两处同名项被无意收紧——MGRS 覆盖 180 → 50 ms（3.6 倍）、
   MGRS 邻接 12 → 2.5 ms（4.8 倍），而本机实测覆盖项平均 30.7 ms，余量不足 40%。
6. **进程级永久缓存没有被文档化**（8.2 已补）：`isea4h_engine.py:38` 的 `_COVER_INDEX_CACHE`
   按 level 缓存全层外接框，无上限、无失效入口；同一进程侧还有 MGRS 几何/域的两组有界 `lru_cache`
   （`CHANGELOG.md:10` 记 8,192 / 32,768 条），只有 isea4h 这份是无界的。
7. **SDK 与 HTTP 的能力集不等价**：14 个公开方法中 `locate_space_code`/`locate_space_codes`
   没有 HTTP 路由，而它们已被碳卫星生产链路与性能烟测使用（`carbon.py:187,1100-1105`、
   `perf_smoke.py:50`）。若按“格网编码接口”做 HTTP 对接点验，必须先明确“点定位到编码”只能走
   进程内 SDK，否则会被当成缺能力。
