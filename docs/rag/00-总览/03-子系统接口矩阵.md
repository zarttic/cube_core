## 0. 怎么读这份文档

### 0.1 四种「接口形态」——先分清，否则会把不存在的东西当成存在

本项目里被称为「接口」的东西，实际落在四种完全不同的形态上。大纲表 3/表 4 把 11 条全部
写成「WEB服务」，**这是与代码不符的**，必须逐条区分：

| 形态 | 含义 | 在本文中的写法 | 典型例子 |
| --- | --- | --- | --- |
| **HTTP** | 跨进程、可被任意语言的客户端调用，有方法+路径 | `POST /v1/...` | `NBJK-006` 数据载入剖分接口 |
| **库表耦合** | 两个子系统读同一张 OpenGauss 表，没有 HTTP 边界 | `表 cube_v3.partition_tiles` | `NBJK-001/002` 剖分数据加载/查询 |
| **进程内 SDK** | 同进程 `import` 调用，无网络往返 | `CubeEncoderSDK().cover(...)` | `NBJK-005` 离散格网编码接口 |
| **对象存储 API** | 走 MinIO 的 S3 兼容 API，不是自研接口 | `PUT s3://cube/...` | `NBJK-004` 剖分瓦片存储接口 |

### 0.2 证据等级

| 等级 | 含义 | 本文标记 |
| --- | --- | --- |
| **实测** | 有可复跑的 curl / TestClient 输出，或浏览器实测记录 | 标注「实测」 |
| **代码** | 有 `文件:行号` 支撑，未在运行实例上调用 | 默认（未特别标注即属此级） |
| **文档** | 来自仓库内既有文档/报告，代码未复核 | 标注「来源：文档」 |

无法确认的一律写「未能确认」，不猜。

### 0.3 实现状态取值

`已实现`（有真实执行路径且被调用） / `部分实现`（路径存在但有明确缺口） /
`未实现`（代码里根本没有） / `仅有占位`（函数或路由存在但无业务动作）。

### 2.2 逐条说明（只写表格表达不了的）

### 7.2 三条工程结论

1. **本项目真正的跨子系统集成方式不是 HTTP，而是共享库表。**
   ② 写 `cube_v3.partition_*`、③ 读；③④ 写 `test.download_orders`、⑤ 读并回写。
   两条最关键的跨子系统链路（数据加载、订单统计）都没有 HTTP 边界。
   接手时必须先拿到的不是接口文档，而是**库表契约**。
2. **认证是「一中心 + 三形态」。**
   ⑤（`.182`）是唯一认证中心，②③④⑤ 都通过它做 SSO；但落到各子系统的鉴权严格程度差异极大：
   ①②⑤ 有 Bearer/权限码，③④ 靠请求头声明身份，⑥ 完全无鉴权。
   「统一身份认证」在测试证据上只能证明「登录跳转 + token 校验」，不能证明「所有接口都做了权限控制」。
3. **外部接口是当前最大的交付不确定性。**
   `WBJK-002` 完全缺失、`WBJK-003` 真实联调未完成、`WBJK-001` 的回环反馈已从 HTTP 回调
   改为写库且对端 mock 缺路由。大纲把三条都标注为「不可测试」，代码现状与这个标注是一致的——
   但不能因此把它们从交付清单里划掉，需要书面澄清责任方。
