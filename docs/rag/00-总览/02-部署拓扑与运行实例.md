### 1.4 「本机开发环境」= `poufennode01`（易错点）

写作规范与既有手册把三份代码落点记为 A/B/C，其中 A 是「本机」。本次实测确认：

- `hostname` = `poufennode01`，`10.3.100.179/24`；
- 本机曾是 **裸机 Ray worker 节点**（`ray-worker.service`，指向 `10.3.100.182:6379`）；该服务 2026-09-18 复核为
  `inactive`/`disabled`，生产算力已迁至 KubeRay（§4.4）；
- 本机同时是 **MinIO 分布式集群的一个节点**（`minio.service`，`/data/minio` 在 NFS 上）；
- 本机同时是 **K8s 集群的节点**（`kubelet.service` + `kube-proxy --hostname-override=poufennode01`，
  2026-09-18 复核为 Ready 但 `SchedulingDisabled`，见 §4.5）；
- 本机不是「离线开发机」：`50039/50040` 是真实对外服务的门户实例。

因此本文件把第三台机器统一写作 **`.179`（`poufennode01`，本机）**，
并提醒：读 A 仓代码时，**运行的进程就是读到的代码**（同一份工作区，见第 5 节）。

### 3.7 三个容易踩的坑

1. **`.182:6000` 有两个 python 进程共享同一 socket**——这是 `uvicorn.run(reload=True)`
   （C 仓 `backend/app/main.py:402-409`）的 reloader/子进程结构，不是两个服务实例。注意：
   `start-tmux-services.sh:10` 的启动命令是 `uvicorn main:app`（**没有** `--reload`），而线上
   实际由 `python main.py` 启动且内部开启 reload；2026-09-18 复核 `.182` 上已无 tmux 会话
   （`tmux ls` 连不上 server），说明服务被手工重启过。
2. **`.165:8081` 配置默认是 `127.0.0.1`，但从本机能访问**——说明 GeoServer 实际绑定并非仅回环，
   与配置默认值不一致（也可能被其他配置文件覆盖）。以探测结果为准，配置值为参考。
3. **`.179:10250` 是 K8s kubelet，不是「某个服务」**——它是 `.183` 集群的节点组件；
   而 `.182:10250` 是另一套遗留 kubeadm kubelet（`kubelet.conf` 指向 `.174:6443`），两台机器的

### 5.3 为什么「部署版本 = commit」在这套环境里不成立

三个原因，都可复现：

1. **两个后端都带自动重载**：`.182` 的后端由 `python main.py` 启动，内部 `uvicorn.run(reload=True)`；B 仓 `dev_up.sh:826-829`
   也在 `BACKEND_RELOAD` 为真时加 `--reload`（并对 `backend/`、`docs/` 做 `--reload-dir`）。
   改文件即生效，进程不会重启，PID 也不变。
2. **启动命令与脚本不一致**：`start-tmux-services.sh:10` 写的启动命令是 `uvicorn main:app`（无 `--reload`），
   而线上实际由 `python main.py` 启动；2026-09-18 复核 `.182` 上已无 tmux 会话。
   → 用脚本内容推断线上状态会出错。
3. **工作区不一定等于 HEAD**：C 仓 2026-09-18 复核 56 项未提交改动，这些改动**正在被服务加载**；
   A 仓 2026-09-18 代码未改（`dead6bf5`），是三个仓库里唯一能对得上 commit 的一份。

实操建议（给接手人）：

- 判断「线上跑的是什么代码」的方法：`ps -o lstart,cmd -p <pid>` 取**启动时刻**，
  再用 `git log --since` 和 `git status` 判断那一刻的工作区内容；**不要**只看 HEAD。
- 复现线上行为时，必须在**同一份工作区**上复现，而不是 `git checkout HEAD`。
