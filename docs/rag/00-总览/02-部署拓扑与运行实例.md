# 02 部署拓扑与运行实例

> 一句话定位：本文件回答四个问题——**有几个系统、跑在哪台机器上、谁调谁、哪份代码属于哪个仓库**。
> 读完它应该能独立判断「某个页面打不开时该去哪台机器、看哪个进程、查哪个仓库」。
> 它不重复六个子系统的功能细节（那在 `10-技术手册/T1~T6`），只描述**部署事实与运行实例**。
>
> - 证据采集时间：**2026-09-12 17:20~17:40（+0800，本机时钟）**
> - 取证方式：本机（`poufennode01`）只读命令 + 对 `10.3.100.182` 的只读 SSH + 对全部涉网
>   端点的 TCP/HTTP 只读探测 + 三份只读代码快照。**未重启、未修改任何服务或仓库。**
> - 本机自报身份：`hostname=poufennode01`，`ip -4 addr` = `10.3.100.179/24`（实测，
>   见第 9 节）。**「本机开发环境」就是 `10.3.100.179` / `poufennode01`**，不是一台独立于
>   集群外的开发机——这一点在第 1.4 节专门说明。

## 0. 证据分级（全文通用）

| 标记 | 含义 | 判定方式 |
| --- | --- | --- |
| **实测监听** | 该端口此刻真的有进程在 LISTEN | `ss -ltnp` 输出（本机与 `.182` 为 root 视角，进程名可见） |
| **探测可达** | 从本机 TCP connect 或 HTTP 请求成功（远端无 `ss` 权限时用） | 第 9 节给出可复跑命令与当时的返回码 |
| **仓库证据** | 只来自启动脚本/配置文件/只读快照，本次**未**在运行时核实 | 标出 `文件:行号` |
| **未核实** | 有配置或文档提及，但既无运行时观测也无权威代码依据 | 写「未核实」，不猜 |
| **未能确认** | 主动查过但拿不到结论（缺权限/缺连接/缺文件） | 写明为什么 |

全文不抄录任何口令、密钥、Token 值；只写变量名、文件位置与用途。凡涉及凭据处均以
「明文存储（值不记录）」描述。

### 1.4 「本机开发环境」= `poufennode01`（易错点）

写作规范与既有手册把三份代码落点记为 A/B/C，其中 A 是「本机」。本次实测确认：

- `hostname` = `poufennode01`，`10.3.100.179/24`；
- 本机同时是 **Ray worker 节点**（`ray-worker.service`，指向 `10.3.100.182:6379`）；
- 本机同时是 **MinIO 分布式集群的一个节点**（`minio.service`，`/data/minio` 在 NFS 上）；
- 本机同时是 **K8s 集群的节点**（`kubelet.service` + `kube-proxy --hostname-override=poufennode01`）；
- 本机不是「离线开发机」：`50039/50040` 是真实对外服务的门户实例。

因此本文件把第三台机器统一写作 **`.179`（`poufennode01`，本机）**，
并提醒：读 A 仓代码时，**运行的进程就是读到的代码**（同一份工作区，见第 5 节）。

1. **物理上只有三个 Web 后端进程**：`.182:6000`（T1+T5）、`.179:50039`（T2+T6 的调用方）、

2. **六个子系统中有两个是「进程内子集」**：T5 与 T1 同进程同库（`C 仓 backend/app`），
   T4 与 T3 同进程同库（`B 仓 backend/`）。
3. **T6 不是服务**：`cube_encoder` 独立 HTTP 服务（默认 `:50012`）当前**未启动**，
   生产链路上它只是被 import 的库（T6 手册 2 节）。

### 5.3 为什么「部署版本 = commit」在这套环境里不成立

三个原因，都可复现：

1. **两个后端都带自动重载**：`.182` 的后端进程命令行含 `--reload`；B 仓 `dev_up.sh:826-829`
   也在 `BACKEND_RELOAD` 为真时加 `--reload`（并对 `backend/`、`docs/` 做 `--reload-dir`）。
   改文件即生效，进程不会重启，PID 也不变。
2. **启动命令与脚本不一致**：`start-tmux-services.sh:10` 写的启动命令**没有** `--reload`，
   但线上进程有。说明这个 tmux 会话里的服务被人工重启过（在 pane 里手动执行了带 `--reload` 的命令）。
   → 用脚本内容推断线上状态会出错。
3. **工作区改动量巨大**：C 仓 34 改 + 17 未跟踪；A 仓 12 改 + 3 未跟踪。这些改动**正在被服务加载**。

实操建议（给接手人）：

- 判断「线上跑的是什么代码」的方法：`ps -o lstart,cmd -p <pid>` 取**启动时刻**，
  再用 `git log --since` 和 `git status` 判断那一刻的工作区内容；**不要**只看 HEAD。
- 复现线上行为时，必须在**同一份工作区**上复现，而不是 `git checkout HEAD`。
