# U4 资源调度 操作手册

> 一句话：把大批量计算任务交出去，看它们在队列里排队、执行、失败重试，并管好自己用掉的额度。
> 适用角色：普通用户、高级用户、科学家团队（有「作业编排」「状态与自愈」）；操作员、管理员（另有「队列调度」「配额与限流」，管理员还有「性能测试」）。
> 入口：登录后点顶部导航「资源调度」，打开 http://10.3.100.165:5176/#/dispatch/orchestrate
> 从其它门户点「资源调度」时浏览器会跳到 `10.3.100.165`，地址栏主机名变化是正常的；未登录时会先跳到统一登录页，登录后自己跳回来。
> 说明：本手册的界面与数字为 2026-09-12 在真实运行实例上实测所得，采集账号是管理员。

## 1. 这个子系统能做什么

1. 把多个算子串成一条流水线，并保存成可复用的函数，下次直接调用。
2. 按三个服务等级排队：紧急、计算、导出；同级任务轮流领取，不让一个大任务独占。
3. 让管理员把排在队里的任务设为紧急，插到别人前面先跑。
4. 统计每天的任务提交次数、导出次数、导出数据量，并限制短时间内的重复操作。
5. 失败后按设定次数自动重试；次数用尽交给人处理，改完参数可以只重跑失败的部分。
6. 给出成功率、失败率、平均耗时、队列效率、算子质量等运营数字。

## 2. 谁能用、需要什么准备

| 角色（登录时选的） | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 普通用户、高级用户、科学家团队 | 进「作业编排」设计流水线、保存函数；进「状态与自愈」看自己任务的历史与失败原因，有重跑入口时重跑。科学家团队还可以提交需要并行执行的任务 | 看不到「队列调度」「配额与限流」「性能测试」；不能给别人加急，不能改配额 |
| 操作员 | 按管理员授予的资源调度权限显示入口：有查看权限时可进「队列调度」「配额与限流」「状态与自愈」；有操作权限才能「设为紧急」和改配额策略 | 看不到「作业编排」「性能测试」；没有被授予的模块不显示入口 |
| 管理员 | 五个标签全部可见：作业编排、队列调度、配额与限流、状态与自愈、性能测试；可给任意账号加急、改配额策略 | 不能让集群总量变大；配额本身由配额账本约束 |

前置条件：

- 账号已开通并下发了「资源调度」相关权限。能看到哪几个标签取决于账号权限，本次配图用的是管理员账号。
- 要计算的数据先在上游准备好（数据包或个人数据空间里的资产），否则编排出来的流水线没有输入。
- 浏览器已登录（全系统共用一套登录入口，账号由管理员开通）。

## 3. 操作步骤

### 3.1 作业编排：把算子串成一条流水线

适用角色：所有能看到「作业编排」的账号。预计耗时：几分钟（取决于函数个数与连线数）。
前置条件：要用的算子已经在函数库中发布。

**第 1 步**：顶部导航点「资源调度」，再点「作业编排」。→ 默认停在「编排设计」，左侧是函数库（本实例 30 个函数），中间是画布，默认是空的（配图为了演示已放进一个算子），右侧是「连接建议」。

**第 2 步**：在左侧「搜索算子」输入关键字过滤函数。→ 列表只剩名称匹配的函数卡片。

**第 3 步**：点一个函数卡片，或把它拖进中间画布。→ 画布上出现该算子的节点；工具栏的计数变成「1 个节点 / 0 条连接」。

**第 4 步**：点节点上的一个输出端口。→ 右侧「连接建议」列出可以接上的下游算子。

**第 5 步**：再点下游节点上同类型的输入端口。→ 两个节点之间出现连线，「条连接」的计数加 1。节点上写清了输入输出类型（例如 raster / raster），类型对不上就接不上。

**第 6 步**：放错了就点节点右上角的叉号删掉，然后继续放节点、连线。→ 画布与计数同步变化。

**第 7 步**：点「保存函数」。→ 弹出「保存函数」窗口，填一个函数名（首字符用字母）后点「保存」，页面提示「函数已保存，可在 Notebook 的“我的项目”中查看。」保存的函数不在左侧函数库里，要复用它请到「剖分数据服务 → 数据在线计算」的 Notebook「我的项目」中调用（详见 U3 操作手册）。

![U4-01 作业编排的函数库与编排画布](../30-截图/annotated/U4-01-作业编排-函数库与编排画布.png)

看一次运行到底跑到哪一步，用同一个页面上方的「运行记录」：

**第 1 步**：点「运行记录」。→ 左栏是「计算任务」，中间是「依赖图」，右下是「日志预览」。

**第 2 步**：用左栏上方的分段按钮在「运行中」和「已完成」之间切换。→ 列表随即切换，两个按钮上各写着条数。

**第 3 步**：点列表里的一行。→ 右侧换成这次运行的依赖图、步骤详情、运行历史和日志预览。

**第 4 步**：看「依赖图」下面那一排数字。→ 完成节点、活动节点、重试次数、耗时；分子追上分母（例如 5 / 5）才代表这次运行全部跑完。

**第 5 步**：失败时看下方的「运行历史 / 事件 / 产物」和「日志预览」。→ 每一步的状态、提交与结束时间、说明都在这里。

### 3.2 队列调度：看任务在排队还是已经跑起来

适用角色：操作员、管理员（需要管理员授予资源调度查看权限；普通用户看不到这个标签）。预计耗时：看数字 1 分钟；查一条工作项 1 分钟。
前置条件：账号已登录并有资源调度查看权限。

**第 1 步**：点「队列调度」。→ 停在「实时调度」：上面是「调度总览」，右边是「工作项查询」，下面是三级「服务等级队列」。

**第 2 步**：先看四个数字和右上角的徽标。→ 排队任务、执行任务、重试队列、失败任务；这一页约每 5 秒自动刷新一次。徽标「就绪」表示队列空，「活跃」表示有任务在排队或执行中，「关注」表示有重试或失败偏多，「断连」表示监控拿不到数据。

**第 3 步**：点 P0、P1、P2 任意一级的标题行展开。→ 列出这一级的活跃任务；该级没有任务时显示「当前队列没有排队或运行中的任务。」

**第 4 步**：找到卡住的任务，点它右侧的「明细」。→ 展开任务 ID、运行实例、队列与服务等级、优先级、作业汇总、提交与开始时间、最新作业。

**第 5 步**（有操作权限时）：点这条任务上的「设为紧急」。→ 任务转入 P0 紧急级，下一次领取时排在最前。想还原就点同一位置的「恢复常规」。

说明：本实例抓图时（U4-03）三级队列都是 0 个任务，看不到「设为紧急」和「恢复常规」这两个按钮，它们只对状态为「排队中」的任务出现；某一级没有任务时，展开后显示「当前队列没有排队或运行中的任务。」下面第二张配图（U4-04）用「工作项查询」查了一条历史任务，示范「明细」展开后的样子（查询出来的那条不是当前排队任务）。

![U4-03 服务等级队列与优先级](../30-截图/annotated/U4-03-队列调度-服务等级队列与优先级.png)

**第 6 步**：点「刷新已展开队列」。→ 已展开的那一级重新拉取任务清单。

**第 7 步**：用「工作项查询」找一条具体的工作项。按任务查：下拉选「任务 ID」，填 TASK- 或 EXPORT- 开头的编号，点「查询」。→ 下面自动展开命中的那一级，只显示这一条，卡右上写「工作项查询结果」。按用户查：下拉切到「用户 ID」，这里只能填数字用户编号（填登录名会提示「请输入有效的用户 ID。」；不知道编号时请管理员代查，或改用「任务 ID」模式），点「查询」。→ 三级队列里显示该用户所有活跃的工作项，卡右上写「用户 <编号> 的活跃工作项」。点「清除」退出查询状态。

![U4-04 工作项查询与任务明细](../30-截图/annotated/U4-04-队列调度-工作项查询与任务明细.png)

**第 8 步**：要看整体效率，点上面的「运营分析」。→ 任务成功率、失败率、平均端到端耗时、资源使用趋势、队列效率和算子质量。

### 3.3 配额与限流：看自己用掉了多少、什么时候会被挡住

适用角色：操作员、管理员。普通用户一般看不到这个标签，需要时请管理员代查。预计耗时：1 分钟。
前置条件：要查别人的用量时，得知道对方的账号名（例如 `admin`，就是登录时用的那个名字）。
注意：这一页管的是「次数」类额度（提交次数、导出次数、导出数据量）和短时间窗口的限流。CPU 与存储额度不在本页，看不到并不代表没有限制；需要更多额度时联系管理员，由管理员在后台管理里调整（见 U5 操作手册）。

**第 1 步**：点「配额与限流」。→ 顶部是「配额与限流」卡片，右上角是运行状态徽标。

**第 2 步**：在「用户 ID」里填账号名（例如 `admin`，管理员可以填任意账号），点「查询治理概览」。→ 右侧六个数字刷新。这一页认的是账号名，不是「队列调度 → 工作项查询」里那种纯数字的用户编号。

**第 3 步**：读当天的用量。→ 今日任务提交、今日导出下载次数、今日导出下载量；再往后三个是已达到限流阈值、接近限流阈值、今日限流触发。本实例 2026-09-12 的读数是任务提交 4 / 1111、导出下载 2 / 24、导出下载量 0 TB / 4 TB，这些数字会随使用变化。

**第 4 步**：看下面的「限流规则」。→ 四类动作各一条：任务提交、用户检索、计算结果下载、数据导出下载；每行给出当前窗口已用次数与限流上限，例如任务提交 80 次 / 2 分钟。进度条越满越接近被拒。

**第 5 步**：要改额度，改右侧「策略调整」里的每日配额与窗口限流。→ 改动在点「保存用户策略」后生效；这一步需要操作权限，权限不足时这里显示的是提示文字而不是输入框。注意：本页每 5 秒自动刷新一次，刷新会把「策略调整」的输入框重置成当前已保存的额度；填完请马上点「保存用户策略」，数字要是被刷回去了，重新填一次再立刻保存。

### 3.4 状态与自愈：任务失败以后怎么办

适用角色：所有能看到「状态与自愈」的账号。预计耗时：看结果 1 分钟；重跑 2~3 分钟。
前置条件：列表里已经有失败或需要人工处理的任务。

**第 1 步**：点「状态与自愈」。→ 上面是三个汇总数字（任务总数、成功 / 失败、运行 / 重试中），下面是「已提交历史任务列表」。

**第 2 步**：点右上角「刷新列表」。→ 列表更新。这一页不会自动刷新，判断任务是否结束前请先点一下。

![U4-06 顶部汇总、刷新按钮与底部分页](../30-截图/annotated/U4-06-状态与自愈-顶部汇总与分页.png)

**第 3 步**：看状态列。→ 常见取值：成功、排队中、执行中、重试中、重跑中、等待人工处理、失败。「重跑中」是刚点过「提交重跑」的任务，稍后会变成排队中或执行中；「等待人工处理」表示自动重试已经用尽，需要人来决定下一步；「失败」表示系统判定重跑也没用。

**第 4 步**：用底部的「上一页 / 页码 / 下一页」翻页找有问题的任务。→ 出问题的任务不一定在第一页。本实例当时共 1488 条、75 页，配图里那两条是在第 2 页找到的。

**第 5 步**：在「等待人工处理」那一行点「调整参数后重跑」。→ 打开重跑窗口，窗口里写着要重跑的任务编号和这次允许改的参数。

**第 6 步**：改完参数点「提交重跑」；不改或不想重跑就点「取消」或窗口右上角的「关闭」。→ 「提交重跑」会真的再算一次，消耗当天的任务数并占用集群资源；「取消」和「关闭」都只是关掉窗口，不产生任何提交。提交后这一行的状态会先变成「重跑中」，稍后变成排队中或执行中。

![U4-07 失败任务与重跑入口](../30-截图/annotated/U4-07-状态与自愈-失败任务与重跑入口.png)

![U4-08 调整参数后重跑窗口](../30-截图/annotated/U4-08-状态与自愈-调整参数后重跑窗口.png)

关于自动重试：系统可以在任务失败后按设定的「最大尝试次数」自动重试，两次尝试之间的等待时间逐次翻倍，次数用尽后状态才变成「等待人工处理」。重试次数由平台与算子决定，当前界面上没有设置它的输入框，详见技术手册 T4 第 8.4 节。

### 3.5 性能测试：管理员做基准测试用

适用角色：管理员。预计耗时：看结果 2 分钟，压测本身的时间由测试项决定。
普通用户可以跳过这一节，这一页不影响你提交和查看任务。

**第 1 步**：点「性能测试」。→ 页面标着「管理员 / 性能」，列出五项验收指标，每项一张卡片。

**第 2 步**：看每张卡片右上角的「达标 / 未达标」和卡片里的指标表。→ 达标表示达到预设要求，未达标表示当前值没到目标，需要管理员排查。

**第 3 步**：展开「测试条件与方法」。→ 写清这一项怎么压、压多久、目标是什么。

**第 4 步**：需要复测时点「启动测试」。→ 会真的向集群发起一轮压测；压测期间不要再往集群提交重任务。点右上「刷新结果」可以更新读数，下方的「历史 / 最近运行」留每次的结果与说明。

## 4. 结果在哪看

| 想看什么 | 去哪里看 |
| --- | --- |
| 一条任务是成功、失败还是还在跑 | 「状态与自愈」的列表与三个汇总数字 |
| 队列堵不堵、有几条在排队和执行 | 「队列调度 → 实时调度」的「调度总览」 |
| 某一级队列里具体有哪些任务 | 「队列调度 → 实时调度」展开 P0 / P1 / P2 |
| 整体成功率、平均耗时、各算子质量 | 「队列调度 → 运营分析」 |
| 一次运行的步骤、状态、时间与日志 | 「作业编排 → 运行记录」 |
| 自己或某个账号当天用掉多少额度 | 「配额与限流」 |

- 确认一条任务成功的标志：状态列显示「成功」，并且「运行记录」里完成节点等于步骤总数。
- 多久能看到：排队时间取决于集群忙不忙；执行时间按数据量变化。运营分析里有实测口径，本实例 7 天口径的平均端到端耗时是 2 小时 01 分，其中「NDVI 计算」平均执行 1 小时 05 分，这些数字会随数据变化。
- 计算产生的数据文件由上游「剖分数据服务」的个人数据空间管理，不在本子系统的页面里，详见 U3 操作手册。

## 5. 出错怎么办

| 我看到的提示或现象 | 可能原因 | 我该怎么做 |
| --- | --- | --- |
| 任务长期停在「排队中」，队列里还标着等待原因 | 集群忙，或自己（团队）的 CPU 配额正被别的任务占满 | 等正在跑的任务结束。真的着急，请管理员在「队列调度」里把这条任务设为紧急 |
| 任务状态是「等待人工处理」 | 自动重试已经用尽 | 先看同一行的「失败原因」，点「调整参数后重跑」，改完参数再提交 |
| 任务状态是「失败」，但「操作」列只有「--」 | 属于重跑也没用的错误，常见是所需资源超过账号额度上限 | 把任务编号交给管理员，请他们从后台排查 |
| 「调度总览」的徽标变成「关注」，失败任务不为 0 | 近期有失败或重试积压 | 到「状态与自愈」按提交时间翻页，看失败原因 |
| 提交任务被拒，提示与配额或限流有关 | 当天的任务提交次数用完，或某个窗口的次数到顶 | 等下一个窗口或第二天再提交；管理员可以到「配额与限流」页看是哪一项顶格。普通用户看不到这一页，把提示文字原样交给管理员 |
| 刚提交的任务在列表里找不到 | 这一页不自动刷新；任务也可能不在第一页 | 点「刷新列表」，再翻页找 |
| 画布上的「保存函数」点不动 | 画布上还没有节点 | 先从左侧函数库点一个函数进画布 |
| 「连接建议」一直是空的 | 还没选任何输出端口 | 先点画布节点上的一个输出端口 |
| 「性能测试」页面上有「未达标」 | 上一次压测没有达到预设目标 | 由管理员判断是压测环境还是服务本身的问题；普通用户不需要处理 |

## 6. 常见问题

1. 提交任务会占用集群资源吗？会。任务一旦开始执行就真的占用 CPU 与内存，直到跑完。
2. 在「编排设计」里画图、保存函数会占资源吗？不会。那只是配置；只有把函数跑起来才算任务。
3. 「设为紧急」会把别人正在跑的任务停掉吗？不会。它只是让这条还在排队的任务先被领取，正在执行的任务不受影响。
4. 正在执行的任务能设为紧急吗？不能。只有还在排队的任务才会出现「设为紧急」。
5. 我能自己改配额吗？不能。改配额属于管理动作，本页的「策略调整」只有具备操作权限的账号（例如管理员）能用。
6. 每天的提交次数在哪里看？「配额与限流」页顶部，本实例管理员账号当时是 4 / 1111。
7. CPU 和存储额度在哪里看？本页不显示，需要管理员在后台管理里查看；要更多额度就联系管理员申请，详见 U5 操作手册。
8. 失败的任务会自动重试吗？会按「最大尝试次数」重试，等待时间逐次翻倍；次数用尽后变成「等待人工处理」。详见技术手册 T4 第 8.4 节。
9. 因为资源不够被退回队列，算失败吗？不算，也不消耗重试次数。任务回到排队，等资源空出来再跑。
10. 一次能提交多少任务？没有固定条数，同时受每日提交次数、窗口限流和 CPU 配额三个约束。
11. 「状态与自愈」的数字和「队列调度」的数字为什么不一样？前者是历史任务的累计口径，后者是当前队列的实时口径，两者统计范围不同。

## 7. 我需要注意什么

- 会真的占用集群资源的主要有三种操作：在上游提交计算任务、在「状态与自愈」点「提交重跑」、在「性能测试」点「启动测试」。在「编排设计」里画布与保存函数不占资源。
- 在「配额与限流」点「保存用户策略」不占集群资源，但会立刻改掉那个账号的每日额度：调低可能让对方马上提交被拒。这个按钮只对有操作权限的账号开放，改前先确认对象和数值。
- 「配额与限流」页每 5 秒自动刷新，刷新会把「策略调整」的输入框重置成当前已保存的额度。填完请马上点「保存用户策略」；数字被刷回去了就重新填一次再立刻保存。
- 「设为紧急」抢占的是排队位次，会把排在队里的其他任务往后挤；它不会停掉正在跑的任务。用之前先确认真的着急。
- 配额不足时的典型表现是「排队不动」，不是报错：任务一直在排队，等待原因写着等资源。反复提交不会让它更快跑起来，只会占更多队列位次。
- 每日提交次数或窗口限流用满后，提交会被直接拒绝，要等下一个窗口或第二天。
- 「状态与自愈」列表不自动刷新，汇报结论前先点「刷新列表」。
- 出问题的任务不一定在第一页，按状态翻页找更可靠。
- 配额数值属于账号配置，不要截图外传；本页可以查别人的用量，请按需使用。
- 页面上的所有数字都会随时间变化；本手册引用的数字是 2026-09-12 的快照，只能用来对照口径，不能当成当前值。

### 1. 「3.3 前置条件应改成数字用户 ID」——不采纳

校验意见第 5 条后半要求把 3.3 的「对方的账号（用户 ID）」改成「对方的数字用户 ID（不是登录名）」。实测这个页面的「用户 ID」框收的就是账号名，不是数字编号，因此不采纳，保留「账号名」语义并补了一句对照说明：

- 界面证据：配图 U4-05（`http://10.3.100.165:5176/#/dispatch/govern`，2026-09-12 实测）里「用户 ID」填的是 `admin`，右侧六个数字和下方「限流规则」都正常返回，规则行头写的是「用户 / admin」。
- 接口证据：2026-09-12 19:30 复测 `GET /api/govern/users/admin/overview` 返回 200，`subject.user_id = "admin"`、`role_code = "admin"`；换成 `1` 得到的是另一套默认主体。
- 对照组：「队列调度」的按用户查询（`GET /api/compute/queue/tasks?user_id=...`）只接受纯数字，填 `admin` 返回 422「Input should be a valid integer」。两处要求不同，已在 3.2 第 7 步和 3.3 第 2 步各写明一次。

### 2. 「补一张能看到『设为紧急』的配图」——现场配不到

校验意见第 6 条要求补一张能看到「设为紧急 / 恢复常规」的配图。2026-09-12 19:15 复测时三级服务等级队列里没有任何排队任务，抓不到这两个按钮：

- `GET /api/compute/queue/dashboard` 的 summary 为 `{"jobs": 2236, "running": 0, "backlog": 0, "retrying": 0}`；`GET /api/compute/queue/tasks` 按 P0 / P1 / P2 三次都返回 `tasks: []`，不带筛选的全量列表只有 4 条 `待提交` 任务。
- 这两个按钮只在任务状态为「排队中」时出现（前端 `canPromoteQueueTask` 要求 `status === 'QUEUED'`）。制造一条排队任务等于真的向共享集群提交计算任务，超出本次取图「只读浏览」的纪律，因此没有人为造数据。
- 替代做法：补拍 U4-04，用「工作项查询」查一条历史任务并展开「明细」，图上标出工作项查询、命中的队列、任务卡和明细字段，并用图例与正文注明「只有排队中的任务才出现『设为紧急』；本实例抓图时三级队列都是 0 个任务」。

### 3. 「改数字会被 5 秒轮询刷回」——已核实，手册侧修正，产品侧未改
