## 三、文档是怎么做出来的（可信度说明）

这套文档不是"根据文件名推测"写出来的，做法是：

1. **事实来源只有一份：代码。** 三个代码基线——本机 `cube_project`（②⑥）、
   `10.3.100.165:/home/nefu_dev_xc/cube`（③④）、`10.3.100.182:/home/guanwang/my_demo`（①⑤）。
   官方文档只提供功能清单与章节骨架，与代码冲突时以代码为准，并在第 11 节显式标注差异。
2. **每条技术结论都要有落点**：`文件:行` 或一条可复跑的命令。写不出来的标"未能确认"。
3. **独立对抗校验**：6 份技术手册由**另一组** agent 逐条证伪，共核对 **1072 条断言**，
   查出 **99 处错误**（9 严重 / 30 中 / 60 轻）与 42 处遗漏，全部按代码证据修正。
   典型错误包括：把“有函数名”当成“已实现”、行号错位、权限码写错档位、
   把 `created_at` 当成超时判定基准（实为 `started_at`）。

   操作手册同样经过一轮对抗校验：7 份共查出 **91 处问题**（U0 10、U1 12、U2 13、U3 13、
   U4 12、U5 19、U6 12），逐条核实后修正，配图问题一律重新抓图而非绕过。

   8 条内部接口由专门一轮核验，**结论与 `00-总览/03-子系统接口矩阵.md` 独立得出的一致**
   （两批 agent 未互相参考），可视为相互印证。
4. **配图来自真实实例**：全部截图在 `2026-09-12` 当天登录真实运行的系统抓取，
   标注框坐标由浏览器返回的元素位置确定，不是手绘示意。
5. **交付前复核**：关键技术结论由主控逐条实跑复核（见下节"已验证/未验证"）。
