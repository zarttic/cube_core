# 操作手册编写规范（面向一般大众）

本文件是 6 份操作手册的统一契约。与 `00-编写规范.md`（技术手册规范）**是两套不同要求**，
不要混用：技术手册写给维护工程师，要代码行号；操作手册写给业务用户，要能照着点。

## 1. 读者画像

读者是科研人员、业务操作员、项目管理者。他们：

- **不关心**代码、接口路径、表名、行号、容器、日志文件
- **关心**：我要完成什么、点哪里、点了会发生什么、出错怎么办、我这角色能不能做
- 可能第一次用这个系统，也可能隔几个月用一次
- 中文学术/业务背景，但不是软件工程师

因此：**禁止**在操作手册里出现接口路径、数据库表名、代码行号、Python 命令。
需要给技术细节时，写「详见技术手册 T? 第 N 节」。

## 2. 章节模板

每份操作手册严格按以下结构：

```
# U? <子系统名> 操作手册

> 一句话：这个子系统帮你做什么。适用角色：<角色列表>。
> 入口：<真实可点的地址或导航路径>

## 1. 这个子系统能做什么
   用业务语言列 3~6 条能力，每条一行。不写实现方式。

## 2. 谁能用、需要什么准备
   表格：角色 | 能做什么 | 不能做什么
   前置条件：账号、权限、需要的原始数据、需要先完成的上游步骤

## 3. 操作步骤
   3.1 <任务名>（大多数人最常做的第一件事）
       - 适用角色 / 预计耗时 / 前置条件
       - 编号步骤，每步格式：
         **第 N 步**：<动作>。→ <预期看到什么>
       - 每个主要步骤后插入配图：![...](../30-截图/annotated/U?-NN-xxx.png)
   3.2 ...（按任务继续，一个任务一小节）
   任务划分按「用户想完成的事」，不按界面标签机械切分。

## 4. 结果在哪看
   数据/结果落到哪里、怎么确认成功了、多久能看到

## 5. 出错怎么办
   表格：我看到的提示 | 可能原因 | 我该怎么做
   只写用户能自己处理的；需要管理员介入的明确写「联系管理员」

## 6. 常见问题
   5~10 条问答。回答要短。

## 7. 我需要注意什么
   不可逆操作、会消耗配额的操作、需要审批的操作、有并发限制的操作
```

## 3. 配图规则（本手册的核心要求）

**每份操作手册至少 4 张真实标注图**，主流程的每一步都应该有图。

### 3.1 配图怎么来

用 `annotate_spec.py` 在**真实运行实例**上现场抓取并标注，不要用未标注的原图，也不要画示意图。

```bash
cd /home/lyajun/projects/cube_docs_workspace
set -a; . ./.secrets.env; set +a
python3.11 -u tools/annotate_spec.py <你的spec.json>
```

规格 JSON 格式见 `tools/annotate_spec.py` 文件头注释。要点：

- 定位优先用 `text=界面上的原文字`（可复现）；找不到才用 `css=`；最后才用 `xy=x,y,w,h`
- **说明文字不要自己写 ①②③ 序号**，序号会自动画在框左上角
- 输出路径写 `30-截图/annotated/U?-NN-描述.png`（相对 `docs/rag/`）
- `title` 写清界面名与实例地址，便于日后核对

### 3.3 出图后必须自检

**用 read 工具把生成的标注图打开看**。检查三件事：

1. 框是否框在了正确的控件上（框错位置是常见错误）
2. 编号与文字说明是否一一对应
3. 有没有出现豆腐块（说明文字里有字体不支持的字符时会出现方框）

不合格就改 spec 重跑，直到图对为止。**不要把没核对过的图写进手册。**

## 4. 事实来源与纪律

1. **界面事实**以你自己在真实实例上看到的为准（read 截图 / 跑工具）。
2. **业务含义**参考同子系统的技术手册 `10-技术手册/T?.md`，但要把技术语言翻译成用户语言。
3. **不要编造界面元素**。截图里没有的按钮、页面，不许写进步骤。
4. **不要编造操作结果**。你没实际点过并看到结果的，不要写「会弹出 XX 提示」；
   若只能从代码推断，写成「正常情况下应看到……」，或者不写这一步的预期结果。
5. 不写任何口令、密钥。
6. 中文写作，句子短，一句话一件事。不用「此外」「综上所述」「旨在」这类书面套话。

## 5. 质量底线

- 一个从没用过系统的人，照着第 3 节能独立完成主流程。
- 每张配图都能对上手边正在运行的系统（截图日期 2026-09-12）。
- 出错处理覆盖该子系统最常见的 3~5 种失败。
- 明确写出哪些操作需要特定角色、哪些会消耗配额。
