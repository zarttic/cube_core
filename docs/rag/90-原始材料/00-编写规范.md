## 1. 硬性规则

1. **不编造。** 每条技术结论必须能落到 `文件路径:行号`、或一条可复跑的命令与真实输出。
   无法确认的，写「未能确认」并说明为什么（缺依赖/缺权限/缺运行时），**不要猜**。
2. **代码优先于文档。** 官方大纲（`archive/docs/project/分析就绪数据剖分管理系统 (3).docx`，
   表1~表83）只提供功能清单与章节骨架。若代码与大纲不一致，**以代码为准并显式标注差异**，
   不得照抄大纲当事实。
3. **区分实现状态。** 每条功能描述标注：`已实现` / `部分实现` / `未实现` / `仅有占位`。
   依据是代码里有没有真实执行路径，不是有没有函数名。
4. **不写与代码无关的套话。** 不写"本系统采用先进架构"这类无信息量句子。
5. **只读。** 不修改任何被描述仓库的文件，不重启任何服务。可以在本地 `/tmp` 做临时实验。
6. **中文写作**，技术名词保留英文原文（如 `partition_status`、`RayJob`）。

## 3. 写作质量要求

- 表格优先于长段落。段落只说表格表达不了的事。
- 行号必须精确到当前代码版本；引用格式：`backend/api/search.py:120`。
- 引用大文件时给出函数名 + 行号，方便读者跳转。
- 每个子系统技术手册的目标长度：**不少于 400 行**，但**不得灌水**——如果某个子系统代码就是少
  （如 T6 仅 5016 行），篇幅可以小，但 11 节必须都在。
- 若发现足以影响手册结论的严重问题（例如某功能代码里根本没有），在文末加
  `## 附录：勘察中的重大发现`，单独列出。
